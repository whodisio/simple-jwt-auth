# 🌙 dream: decode ops throw a raw SyntaxError on a jwt-shaped token whose segments are not json

kind: repair · owner: simple-jwt-auth maintainers · caught 2026-11-06

## .the cue that fired

an l3 peer review of the `unauthed` subpath route read the decode ops and flagged that `getUnauthedClaims({ token: 'a.b.c' })` passes the shape guard and then throws from `JSON.parse`.

## .the gap, precisely

- `isJSONWebToken` checks the three-segment base64url shape only
- `getUnauthedClaims`, `getUnauthedHeaderClaims`, and `redactSignature` each repeat that guard with the same message
- a token that fits the shape but whose segments do not decode to json reaches `JSON.parse` and surfaces as a bare `SyntaxError`, not `SimpleJwtAuthError`
- the readme promises "self explanatory errors"; a browser consumer that catches `SimpleJwtAuthError` misses this one
- read from code, not yet run

## .the shape of the fix

- one shared segment decoder (e.g. `asClaimsOfTokenSegment({ token, segment })`) that owns the shape guard, the base64url decode, and the json parse
- it wraps a parse fault in `SimpleJwtAuthError` with a message that names the segment (`header` | `body`)
- the three ops compose it; a unit test per op for `'a.b.c'` asserts the class and snaps the message

## .why it is not done in this round

it predates this pr, and the vision's "malformed" covers a shape mismatch only. a change to error behavior on the decode ops is a contract change of its own, best seen by the commander apart from the subpath.
